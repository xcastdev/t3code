# Project MCP catalog

## Goal

Let a user configure MCP servers for one project in T3 Code, choose the providers that receive each server, and see when a change applies.

## Problem

T3 Code attaches its own preview MCP to provider sessions, but users cannot manage external servers in the app. Provider configuration is currently assembled inside adapters, so a project cannot have an explicit, inspectable MCP policy.

## Scope

The first release manages project-scoped remote HTTP MCP servers. A server record has a stable ID, name, URL, enabled state, and the provider instance IDs that may receive it. The record belongs to one project. It does not apply to other projects or to a provider session that began before the change.

The catalog also lists T3-managed MCP entries. Those entries are read-only. The preview MCP remains enabled when the server issues the session credential. A user cannot remove, rename, or replace it.

The server resolves enabled catalog entries when it starts a provider session. Each adapter receives a provider-neutral resolved list and translates it to its native configuration. The list includes an application mode:

- `active-session` for a provider that reloads the configuration without a restart.
- `next-session` for a provider that reads configuration only when T3 starts the session.
- `unsupported` when the adapter cannot attach a remote HTTP MCP server.

The first UI lives in `ProjectSettingsPanel.tsx` for the selected environment and physical project. It lists the server name, URL host, enabled providers, and the application mode for every selected provider. Add, edit, enable, disable, and remove operate on external entries. The list response returns the full URL only to an authorized client of that project, because editing needs it. It rejects URL userinfo and query strings. The client never receives credentials because this release has no credential fields.

## Non-goals

- Local stdio MCP servers, OAuth, headers, environment variables, and secrets.
- Skills, commands, agents, snippets, knowledge, tasks, terminal MCP, and subagent controls.
- A connection-health probe. A configured URL is not proof that the remote server is reachable.
- Retrofitting a changed configuration into a session that cannot reload it.
- Mobile UI. The server contract must remain usable by mobile later.

## Data model

Persist catalog entries in the project record, not `settings.json`. The project already scopes threads and workspace paths, so this preserves project isolation and keeps a server configuration with the project it controls.

`ProjectMcpServer` contains:

```ts
{
  id: McpServerId;
  name: TrimmedNonEmptyString;
  url: HttpUrl;
  enabled: boolean;
  providerInstanceIds: ReadonlyArray<ProviderInstanceId>;
}
```

`McpServerId` is generated by the server. `name` is unique within its project after case folding. It has a maximum of 120 characters. `url` has a maximum of 2,048 characters, must use `https:`, and cannot contain userinfo or a query string. T3 accepts `http:` only for loopback hosts, which keeps local development viable without accepting arbitrary clear-text credentials in a later release. A project holds at most 50 external records. `providerInstanceIds` may be empty. An empty list means the server is saved but attached nowhere.

The read model returns external entries and derived managed entries in separate arrays. The managed array is not part of persistence.

## Provider resolution

Add a narrow `ProjectMcpResolver` service. It takes a `projectId` and the session target, reads that project's enabled entries, filters them by `providerInstanceId`, and returns transport-neutral `ResolvedProjectMcpServer` values. Give `ProviderService` a read-only durable thread-to-project lookup and resolve there, so normal commands, its internal recovery path, and process-restart recovery all use the same code. `ProviderService` cannot infer the project from `ProviderSessionStartInput` alone.

Add `remoteHttpMcp` to `ProviderAdapterCapabilities`, then derive each configured instance's application mode through the registry. Each adapter owns conversion from `ResolvedProjectMcpServer` to its native configuration. A provider that cannot accept remote HTTP MCP receives no external server. A disabled or removed instance is `unavailable`, distinct from `unsupported`; the catalog retains its ID so the user can remove it. T3's preview MCP continues through `McpSessionRegistry` and does not become a catalog row.

Do not infer compatibility from driver names in the UI. The server returns the capability matrix with the project MCP read model. A native config key derives from the immutable server ID, never the display name. Reserve `t3-code` for the managed preview entry.

## API and authorization

Add typed project MCP RPC methods for list, create, update, and remove. `RpcAuthorization.ts` grants environment read scope to list and operate scope to mutations. Each handler then validates project ownership and existence. The web client advertises a server capability before it calls these methods, so a newer client connected to an older environment hides the panel rather than issuing an unknown RPC. The server validates IDs, project ownership, URL policy, unique names, and provider instance IDs before it persists a change.

Only the resolver uses URLs to start a session. Do not expose a generic endpoint that returns all project MCP configuration across projects.

## Acceptance criteria

- A user can add an HTTPS server to Project A, enable it for one provider, and start a new thread. Only that provider session receives the server.
- Project B and disabled providers do not receive Project A's server.
- The UI identifies whether each enabled provider applies the change in an active session, at the next session, or not at all.
- A user cannot alter a T3-managed entry.
- Invalid URLs, duplicate names, and provider IDs absent from the environment fail with actionable errors.
- Existing preview MCP behavior remains unchanged for every provider.
- An external server named `t3-code` receives an ID-derived native key and cannot replace preview MCP.
- A recovered session gets the same project MCP entries as a normal session start.

## Risks and decisions

Provider MCP formats are different, so the shared model stops at a remote HTTP URL. Headers and local commands would broaden the security model and are deliberately deferred. Session creation is the one integration point. Avoid watching catalog changes from every live adapter until a provider has a tested reload mechanism.
