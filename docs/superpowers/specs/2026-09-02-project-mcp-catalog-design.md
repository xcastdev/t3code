# Project MCP catalog

## Goal

Let a user configure MCP servers for one project in T3 Code, choose the providers that receive each server, and see when a change applies.

## Problem

T3 Code attaches its own preview MCP to provider sessions, but users cannot manage external servers in the app. Provider configuration is currently assembled inside adapters, so a project cannot have an explicit, inspectable MCP policy.

## Scope

The catalog manages project-scoped MCP servers using stdio, Streamable HTTP, and legacy HTTP +
SSE transports. A server record has a stable ID, name, explicit transport, enabled state, and the
provider instance IDs that may receive it. The record belongs to one project. It does not apply to
other projects or to a provider session that began before the change.

The catalog also lists T3-managed MCP entries. Those entries are read-only. The preview MCP remains enabled when the server issues the session credential. A user cannot remove, rename, or replace it.

The server resolves enabled catalog entries when it starts a provider session. T3 owns each
upstream MCP client and exposes one authenticated, opaque per-server proxy endpoint for that
session. Each adapter receives only the provider-safe T3 endpoint and scoped bearer credential,
then translates it to its native remote-MCP configuration. The list includes an application mode:

- `active-session` for a provider that reloads the configuration without a restart.
- `next-session` for a provider that reads configuration only when T3 starts the session.
- `unsupported` when the adapter cannot attach the T3 project MCP proxy.

The first UI lives in `ProjectSettingsPanel.tsx` for the selected environment and physical project. It lists the server name, transport, enabled providers, application mode, and OAuth status for every selected provider. Add, edit, enable, disable, and remove operate on external entries. The list response returns transport metadata and opaque credential references only to an authorized client of that project. Credential values are write-only and live in the server secret store.

## Non-goals

- Skills, commands, agents, snippets, knowledge, tasks, terminal MCP, and subagent controls.
- A connection-health probe. A configured URL is not proof that the remote server is reachable.
- Retrofitting a changed configuration into a session that cannot reload it.
- Mobile UI. The server contract must remain usable by mobile later.
- Live mutation of active provider sessions. Catalog changes apply to the next provider session.

## Data model

Persist catalog entries in the project record, not `settings.json`. The project already scopes threads and workspace paths, so this preserves project isolation and keeps a server configuration with the project it controls.

`ProjectMcpServer` contains:

```ts
{
  id: McpServerId;
  name: TrimmedNonEmptyString;
  transport: ProjectMcpTransport;
  enabled: boolean;
  providerInstanceIds: ReadonlyArray<ProviderInstanceId>;
}
```

`McpServerId` is generated by the server. `name` is unique within its project after case folding. It has a maximum of 120 characters. HTTP URLs have a maximum of 2,048 characters, must use `https:` or loopback `http:`, and cannot contain userinfo or a query string. HTTP headers and stdio environment variables contain opaque credential references; their values are accepted only by mutation inputs and are stored in the server secret store. A project holds at most 50 external records. `providerInstanceIds` may be empty. An empty list means the server is saved but attached nowhere.

The read model returns external entries and derived managed entries in separate arrays. The managed array is not part of persistence.

## Provider resolution and proxying

Add a narrow `ProjectMcpResolver` service. It takes a `projectId` and the session target, reads that project's enabled entries, filters them by `providerInstanceId`, and returns transport-neutral `ResolvedProjectMcpServer` values. Give `ProviderService` a read-only durable thread-to-project lookup and resolve there, so normal commands, its internal recovery path, and process-restart recovery all use the same code. `ProviderService` cannot infer the project from `ProviderSessionStartInput` alone.

Immediately before adapter startup, the server issues a provider-session bearer token and an opaque
random endpoint handle for each resolved project server. The proxy registry snapshots the complete
redacted transport and credential references under that session. On first request it resolves
credential values, opens the upstream client lazily, and brokers MCP operations through the T3
endpoint. It never rereads the current catalog for an active session. Session stop, thread deletion,
credential expiry, OAuth disconnect, and server shutdown close every upstream process, HTTP
connection, and SSE stream.

The proxy uses MCP TypeScript SDK v2. It negotiates the `2026-07-28` modern era and the SDK legacy
range from `2024-10-07` through `2025-11-25`. Streamable HTTP compatibility fallback creates a
fresh legacy client and SSE transport only after initialization returns 400, 404, or 405. The
semantic broker preserves standard operations, notifications, cancellation, subscriptions,
pagination, discovery, and multi-round-trip input-required behavior. Extensions pass unchanged
only between peers in the same era; an explicit adapter is required for cross-era translation.

Add `projectMcpProxy` to `ProviderAdapterCapabilities`, then derive each configured instance's application mode through the registry. Each adapter owns conversion from `McpIssuedProjectServer` to its native configuration. A provider that cannot accept the project MCP proxy receives no external server. A disabled or removed instance is `unavailable`, distinct from `unsupported`; the catalog retains its ID so the user can remove it. T3's preview MCP continues through `McpSessionRegistry` and does not become a catalog row.

Do not infer compatibility from driver names in the UI. The server returns the capability matrix with the project MCP read model. A native config key derives from the immutable server ID, never the display name. Reserve `t3-code` for the managed preview entry.

## API and authorization

Add typed project MCP RPC methods for list, create, update, and remove. `RpcAuthorization.ts` grants environment read scope to list and operate scope to mutations. Each handler then validates project ownership and existence. The web client advertises a server capability before it calls these methods, so a newer client connected to an older environment hides the panel rather than issuing an unknown RPC. The server validates IDs, project ownership, URL policy, unique names, and provider instance IDs before it persists a change.

Only the resolver and proxy registry use upstream URLs to start a session. Do not expose a generic
endpoint that returns all project MCP configuration across projects. The public project endpoint
contains only an opaque handle and requires the provider-session bearer token.

## Acceptance criteria

- A user can add an HTTPS server to Project A, enable it for one provider, and start a new thread. Only that provider session receives the server.
- Project B and disabled providers do not receive Project A's server.
- The UI identifies whether each enabled provider applies the change in an active session, at the next session, or not at all.
- A user cannot alter a T3-managed entry.
- Invalid URLs, duplicate names, and provider IDs absent from the environment fail with actionable errors.
- Existing preview MCP behavior remains unchanged for every provider.
- An external server named `t3-code` receives an ID-derived native key and cannot replace preview MCP.
- A recovered session gets the same project MCP entries as a normal session start.

## Risks and decisions

Provider MCP formats are different, so adapters stop at the authenticated T3 proxy endpoint. The
secret store and session lease keep upstream credentials out of events, projections, URLs, logs,
and provider command-line arguments. Session creation is the one integration point. Avoid watching
catalog changes from every live adapter until a provider has a tested reload mechanism. Externally
managed OpenCode remains explicitly unsupported because T3 has no proven mutation path.
