# Per-subagent transcripts and controls

## Goal

Let a user inspect one native subagent's work and, when its provider supports the action, message it, answer its requests, or stop it. The parent thread and sibling agents remain independent. This plan implements the approved scope without terminal access; it does not create T3-managed agents.

## Scope

- In: Web, desktop, and mobile agent views; agent-specific history, live updates, message, approval, and stop actions; local, relay, and tunnel clients.
- Out: Restarting a stopped agent, launching a named managed agent, fabricating a transcript from summaries, or any provider-owned terminal access.

## Acceptance criteria

- [ ] AC-1: Opening a subagent from its parent thread shows a stable identity, parent, provider, role or title, status, and available actions. Nested agents remain distinguishable.
- [ ] AC-2: Available messages and tool activity appear in order. Partial or unavailable provider transcripts are labeled honestly; child narration never appears in the parent chat.
- [ ] AC-3: Live entries and status changes merge without duplicates; reopening after reconnect retrieves persisted history through bounded, pageable reads.
- [ ] AC-4: Where supported, a user can message the selected running or resumable subagent and see the message and outcome in its transcript. A stale or failed send cannot silently target the parent or a sibling.
- [ ] AC-5: A subagent request appears in its view and in the parent thread as a clearly labeled subagent request or permission. Either view answers the same request identity; resolving it in one view updates the other. Late, duplicate, or unauthorized answers have clear outcomes.
- [ ] AC-6: Where supported, Stop targets only the selected subagent, reports success or failure, and leaves the parent and siblings running.
- [ ] AC-8: Available actions reflect the provider, agent, and lifecycle. Unsupported and unverified capabilities have distinct reasons. At least one provider must execute each requested control before that control is called implemented; otherwise stop for a scope decision.
- [ ] AC-9: Web and desktop open the agent view from Agents; mobile opens it from the thread work log. Both return to the parent thread. The web and desktop child conversation uses the same message, Markdown, and tool presentation as the main chat within the sidebar width.
- [ ] AC-10: Server authorization binds reads and actions to the parent thread and environment. Reused native child IDs, stale sessions, forged identities, and provider changes cannot read or control another agent.
- [ ] AC-11: Older threads, parent timelines, status displays, and providers with summary-only activity continue to work.

## Decisions

- Use an opaque T3 agent key bound to environment, parent thread, provider instance, provider session generation, and native child identity. Display IDs and `runHandles` are never control authority. Persisted history survives reconnect; live control handles expire with their provider session and must be revalidated.
- Represent each capability as supported, unsupported, or unverified with a reason. A missing credential or absent probe is unverified, not unsupported. Keep transcript completeness separate from action capability.
- Child content and requests branch from provider ingestion before parent turn/message creation, buffering, checkpointing, or completion. Retain one approval request and resolution lifecycle for both parent and agent views; present child-owned requests in the parent as subagent requests without inserting child narration into parent chat.
- Use orchestration commands, persisted outcomes, reactors, and receipts for actions. Distinguish accepted, completed, failed, and unknown provider outcomes. A timeout after provider acceptance must not blindly resend a message or stop.
- Page reads and subscriptions share one monotonic sequence/watermark. Bound page size, content chunks, client retention, and subscription queues; recover gaps from a cursor rather than replaying the full parent thread.

## Risks and rollback

- Provider support differs by installed version. P1 is a blocking feasibility gate, not a license to substitute summaries for transcripts.
- Child messages must be intercepted before parent orchestration; otherwise parent turns, checkpoints, and streamed text can be corrupted. Retain regression tests for both paths.
- Old clients must continue decoding additive contracts. Additive persistence migrations have no down migration; back up representative state and verify older binaries tolerate new tables/columns before claiming rollback safety.
- Keep action receipts after provider timeouts so the UI can report unknown outcomes without retrying blindly. Revoked sessions invalidate live handles but not persisted history.
