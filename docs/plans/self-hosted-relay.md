# T3 Code self-hosted relay implementation plan

Baseline: 09b04a5d49. Slug: self-hosted-relay. Plan for the agreed specification and subsequent revisions in the parent conversation. No application code, commit, PR, or deployment is part of this planning task.

## Architecture and release boundary

One single-owner relay distribution, with a shared Effect runtime and portable SQLite store. Run it in a desktop-bundled T3 server, an always-on headless T3 server, or an independent Node process. Embedded desktop availability follows the bundled server lifecycle. Standalone opens no environment database and starts no agent providers. Host one active instance for a relay identity. T3 environments remain authoritative for local execution, direct sessions, and peer links.

The relay owns scoped pairing and administration, enrolled environment discovery, authenticated fallback forwarding, activity aggregation, push delivery, external destinations, and opt-in ingress buffering for scheduled tasks. The environment also retains its own adapters and direct task webhooks. Prefer verified direct routes. Support LAN, Tailscale, WireGuard, operator-configured HTTPS or tunnels, and cached direct access when the relay is down. Release scope includes backup and move, exposure controls, and diagnostics. Multi-user tenancy, active-active, managed tunnel provisioning, and upstream store-app push are future work. Private iOS push implementation ships in scope even while hardware evidence is pending.

## Critical design decisions

- Use stable relay and environment identities independent of address. Use the existing T3 scoped one-time grant model with distinct relay and environment audiences. Discovery, forwarding, device preferences and activity entitlement, enrollment, administration, export and recovery are separately checked operations. A client accessing relay Settings through its desktop environment needs local authority for the exact operation and a corresponding relay-issued grant. A device gets an explicit all-environments or selected-environments activity entitlement. Enrolling for publishing never grants access to another environment.
- Public hook ingress is a dedicated, default-off HTTPS listener or vhost that exposes scheduled hooks only. Private administration, discovery, tunnel admission, and interactive access have independent exposure. Interactive relayed browser access uses isolated HTTPS origins per environment, provisioned by the operator. Preserve destination session, OAuth scope ceilings, cookies, WS tickets and CORS boundaries. The operator is trusted with traffic the relay forwards.
- Automatically discovered routes may carry credentials only after identity is authenticated on the connection used. Environment ID alone and a signed preflight followed by a separate connection are insufficient. Preserve explicitly paired direct routes under their existing policy. Unverifiable learned addresses stay candidates until explicit pairing. The proof in P1 determines the supported binding for each surface, including browser limitations and same-origin environment pages. Automatic failover never retries an ambiguous mutation without a durable idempotency key.
- Initial limits proposal: keep 1 MiB hook bodies, 60 requests/minute/hook, 600/minute/environment endpoint, 24-hour hold, and 100 queued items/hook or 1,000 items/50 MiB per enrollment. Add a 250 MiB relay-wide hold cap. Keep 16 external destinations per scope and 10-second send deadline. Start with 2 concurrent probes/environment, a 2-second direct probe deadline, 64 forwarded streams/environment, a 60-second activity lease with 20-second renewals, and 7-day or 10,000-row redacted history. Transport budgets and eviction behavior must be established in P1. Delivery receipts survive history pruning for the full retry window. Keep outgoing alerts live-only through a relay outage and do not resend ambiguous outbound external deliveries.

## Access and durability contracts

| Principal                               | Allowed data and actions                                                                                                                                                                                                                                                                                            |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner or access administrator           | Owner-issued role grants, enroll/revoke, and membership changes within the grant. Owner bootstrap and offline recovery are local administrative operations. Backup export and restore each require their specific privilege.                                                                                        |
| Scoped relay reader or settings manager | Read redacted status, directory, and delivery metadata only within the grant. Change scoped settings or exposure and run destination tests only with write authority. Show task webhook URLs only to a caller with destination authority over that task; ordinary relay reads return status and redacted IDs.       |
| Device session                          | Discover permitted environment names and route hints, read only entitled activity, and modify only its own preferences and token registration. Owner-granted environment membership is separate from editable preferences. Filter source rows before titles, counts, notifications, widgets, and links are derived. |
| Environment enrollment                  | Advertise, publish and maintain a tunnel for its own environment. A separate directory grant can discover allowed peers. Destination permission still controls each peer operation.                                                                                                                                 |
| Forwarded client or peer                | Relay verifies relay admission and allowed destination. The destination independently verifies the application session or peer grant. A relay grant grants no environment authority.                                                                                                                                |

On revocation, reject new work and close affected live streams. Leave independently authorized direct sessions usable after relay revocation. Destination revocation applies over both routes. Reconcile or end the combined activity when a device loses entitlement, including an empty aggregate. Serialize changes that remove effective source access with each send’s final authorization check and initiation of provider handoff. This includes device entitlement changes, device revocation, environment unenrollment, and publisher revocation. Once revocation commits, a queued payload with the stale entitlement version must be dropped or recomputed before handoff. A request already handed to the provider may still display. Test both orderings using a controlled sender. Removing a source must remove its title, counts, terminal content and tap target from subsequent payloads. Removing the last source must send a contentless end without a stale tap target when an activity needs closing. Record pending ActivityKit starts by installation and activity generation. If an update token arrives late for a start submitted before access changed, reconcile it against the current grant. Send a redacted update if the same activity is still valid, or a contentless end addressed to that retired activity’s token. A delayed end cannot use a newer activity’s token. Keep minimal retiring-generation state through the token arrival window, without thread content.

For both the relay hold and the destination receipt plus runnable work, require acknowledged work to survive process failure and an OS crash on storage that honors sync. Use a synced SQLite commit (WAL with synchronous=FULL and platform-appropriate flush settings) for the acceptance transaction. If the existing environment store cannot honor that contract within its performance budget, isolate durable ingress with an explicitly recoverable handoff before ACK. Do not silently use NORMAL for this promise. Charge count and bytes in the same transaction as hold insertion. Recover runnable work by its stable workflow command identity. Receipts span the retry horizon: use seven days from original ingress for v1, reject expired delivery after 24 hours, and stop restored records beyond the hold horizon. Use bounded jobs and warn when durable storage is unavailable.
