Deliver `upstream-main-updated` as an upstream-based application with the approved missing capabilities from `main`, plus individual persistent assistants. Preserve the upstream installation the user actually uses. Preserve current upstream UI/UX and orchestration V2 as the foundations.

## Scope

In scope: durable Project Work/knowledge, GitHub intake, revision-bound guided approval, teams and portfolio/supervision, authorized implementation children, verification/review/evidence/integration/publication guards, project memory, managed MCP/skills/commands/snippets and inventory, missing Source Control index/history functions, recoverable conversation paths, proven transcript/control gaps, shared project PTY tools, Home Assistant notifications, desktop attachment to an independently owned local server, useful V2 work counts, and persistent assistants. Keep the upstream provider ecosystem, Usage, source-control hosts, rich composer, device/mobile, automation, authentication and remote transports.

Keep `$skill`. Adapt missing capabilities to current components, navigation, panel placement, keyboard/focus conventions and responsive behavior. Do not transplant main's old right rail, secondary-pane arrangement or bottom-only terminal layout. Full mobile MCP catalog authoring and provider-specific named native-agent launch systems were not shipped main requirements.

Personal assistants are environment-owned named identities with versioned rules, prompt, personality, provider/model, selected tools/skills and private memory. Each has **one canonical continuous conversation**. Automatic useful-memory capture is enabled, with inspection, correction and forgetting. Configuration alone never starts inference. Optional routines use the existing scheduler and that canonical chat. Topic channels, group chat and assistant-led review/management of Project Work are future; existing Work/team reviewing and management remain in scope.

Managed-provider matrix decisions remain numbered: **14** native plugin exclusion is a future possibility; **15** T3 V2 owns child execution/control, native children only with verified assignment-sufficient controls; **16** native per-turn ceilings are optional, omitted otherwise; **17** no exact internal-request enforcement; **18** providers retain native model authentication, credential convenience/proxy is future; **20** no new Pi-equivalent OS cage, optional file MCP tools are not a sandbox; **21** reuse current process runner and main PTY tools without hard RAM parity. Retain original task deadlines, assignment/depth/concurrency limits, repair authorization and observed usage/uncertainty. No strict token broker or managed Pi SDK worker is a prerequisite.

No import of unused main-installation Work/team/memory/archive records. New domain storage starts empty. No cross-environment assistant replication, advanced inferred profile system, messaging bridge, voice, Hermes runtime bridge or new always-on inference loop.

3. **Atomic admission seam, not another scheduler.** Add a small server-only `RunAdmission` interface in orchestration V2. V2 resolves the authoritative owner from the target thread and any originating owned session, independently of caller-supplied fields. Work or assistant adapters resolve durable fence/configuration references from that binding. Every run-creating or promoting command validates the resolved owner, compares current SQL authority, and binds the admitted run in the same transaction as its existing receipt/events/outbox. Caller references can only narrow or match this authority, never remove it. Replays return the recorded result; revoked authority cannot authorize a different command. Before provider start, queued runs recheck current permission/lifecycle and the retained assignment fence, then use the admitted configuration snapshot. The interface performs SQL-only checks inside the transaction; no model, provider, Git or network effects there. Keep domain-specific checks in their domain adapters and composition, avoiding V2 importing Work modules. Unowned ordinary paths retain upstream behavior. Owned inference is denied while disabled/archived/revoked, including internal continuation and wake paths; pure result recording, archive retention, cleanup and cancellation may proceed without starting inference. Owner lookup and checks are mandatory inside the serial V2 commit and again at provider start, not merely in ThreadManagementService. A durable domain intention can retry the same command; V2 owns effect retries and native recovery. Unproved native starts/stops remain uncertain and retain reservations until reconciliation.
   Descendants inherit Work root/owner/fence/deadline and count against depth/concurrency inside admission commitment. Assistant children inherit selected tool/skill limits and current owner policy but receive no implicit memory-sharing grant. Owned `t3_thread_launch`/`create_threads` cannot escape into unowned top-level work: deny those agent-originated launches with guidance to permitted delegation. Owned `schedule_task` is denied unless the current owner explicitly permits routine creation; allowed assistant routines bind the same assistant through the existing scheduler and cannot launch Project Work. Owner stop/drain traverses all bound descendants, retaining uncertain native outcomes. These T3 admission rules do not sandbox provider-native plugins.

Delayed extraction/index results require matching owner/source revision/generation before applying. Search hydrates against current SQL authority; backend cleanup remains durable until confirmed. Increment a context-memory epoch; invalidate T3 recall caches/summary contributions and, where a native session already received the old fact, use V2 context handoff/session replacement from bounded current context before continuing.
